# Step 8b-2b: facts before the build (2026-11-25)

Read on merrick from the source at origin/main 9c262c2 and from
hashicorp/raft v1.8.0 in the Go module cache. Each answer names the file
and the function.

## 1. hashicorp/raft v1.8.0 `LeadershipTransferToServer`

- `api.go` `LeadershipTransferToServer(id, address)`: refuses only with
  protocol version < 3; then `raft.go` `initiateLeadershipTransfer`
  refuses a transfer to the leader itself ("cannot transfer leadership to
  itself") and an enqueue that cannot go through (`ErrEnqueueTimeout`).
- `raft.go` `leaderLoop`, case `leadershipTransferCh`: the target needs
  only a replication state (`leaderState.replState[id]`), which every
  server of the leader's latest configuration has, **voter or not**: the
  library does not check the target's suffrage when an ID is given
  (`pickServer`, used only without an ID, takes voters only). So the
  caller must pick a voter itself. A second transfer while one runs
  returns `ErrLeadershipTransferInProgress`.
- A target that is not caught up: `leadershipTransfer` keeps triggering
  replication until the target's `nextIndex` is past the leader's last
  index, then sends `TimeoutNow`. The whole transfer is bounded by one
  `ElectionTimeout` (1 s by default); past it the future returns the
  error `leadership transfer timeout`. A failed `TimeoutNow` returns
  `failed to make TimeoutNow RPC to <id>: ...`. Success (the leader left
  its leader loop) returns nil.
- An uncommitted configuration change does not stop it: the transfer
  case is not gated by `configurationChangeChIfStable` (only new changes
  are). While a transfer runs, `Apply`, `Barrier`-like writes, user
  restores, `GetConfiguration` and new configuration changes are answered
  with `ErrLeadershipTransferInProgress`.

## 2. Our dialler and a first byte that is neither 0x01 nor end-of-stream

`internal/cluster/raftnet/peerrpc.go` `confirmAccepted` reads one byte
and returns `unexpected first byte 0x..` for anything but 0x01.
- `transport.go` `DialPinned` turns that into a `*HandshakeError`: a
  failed connection, nothing sent. So every dialler of build cdd5602
  (Raft's pool, `Caller.Call`) treats 0x02 as a failed connection.
- `probe.go` `ProbeKey` maps every non-timeout error of
  `confirmAccepted` to `ProbeRefused`. So an old **probe** (the removed
  notice's check and `join --abandon`) reads 0x02 as "refuses" — exactly
  what it reads today for the silent close that 0x02 replaces. A mixed
  cluster is no worse than today: an old node counts "cannot say" as a
  refusal, as it counted the silent close; a new node counts an old
  node's silent close as a refusal, as today. No protocol version
  change.

## 3. A peer operation name build cdd5602 does not know

`internal/cluster/raftnet/peerrpc.go` `servePeerRPC`: `Allowed(op,
kind)` returns false for an unknown name, and the node answers
`{"ok":false,"code":"forbidden","message":"the operation \"clock\" is not
open to a member key"}`. The caller (`Caller.Call`) gets a
`*PeerError{Code: "forbidden"}`. It can tell that from a network failure
(a `*HandshakeError` or an `*OutcomeUnknownError`), but **not** from a
real refusal of an operation that exists: the code is the same, only the
message text differs. So the clock check (D3) reads every failure and
every error answer as "clock not known", never as "no answer" in any
other check: the status answer is read in its own RPC before the clock
RPC, and only the status RPC decides "answers".

## 4. The agent's audit code

- `internal/auditarchive/segment.go` `writeSegment`: a segment is a
  gzip-compressed JSON Lines file (a header line, then one line per
  entry, columns in a fixed order, `appendEntry`); the hash is SHA-256
  over the whole file as written. `Header.PreviousHash` chains a segment
  to the one before. A segment is sealed by inserting its row in the
  `audit_segments` table of the agent's database. There is **no
  per-record hash chain**: records inside a segment are covered by the
  segment's hash only, and live entries in the database by nothing.
- `internal/auditarchive/verify.go` `Verify` walks the index and the
  files; `internal/auditcmd/auditcmd.go` `Verify` prints one line per
  segment and returns the first break.
- Exit codes of `skep-agent audit verify` (`cmd/skep-agent/main.go`
  `main`): **0** nothing wrong, **1** a break found or verification
  failed, **2** a usage error (`flag.ErrHelp`).
- Pure functions that could be shared: `appendEntry` (canonical line
  encoding of database columns) is unexported and tied to SQL column
  values; the hashing is `crypto/sha256` over a file. Nothing fits a
  per-record chain of JSON records; the cluster audit shares no code with
  it and uses `crypto/sha256` and `encoding/json` directly. Its exit codes
  are the agent's (0, 1, 2).

## 5. A failed write of `state/membership.json`

`internal/cluster/clusterstate/machine.go` `apply`: when the
`MembershipWriter` fails, the machine **stalls** at that entry
("cannot write the applied-membership file: ..."), does not apply it and
does not report it as applied; it applies nothing after it, and health
shows `state_machine` unavailable. `Restore` returns the error and keeps
the old state. The audit write (D4) is handled the same way.

## 6. The entry-version rule

"After 0.2 is released, a change to how an existing entry type is applied
needs a new entry version" is written neither in ADR 0013 B5 nor in
CLAUDE.md (B5 says each build declares the highest version it applies,
and the step 8b-2a entries say version 2 for the guest inventory, but not
the general rule). Amendment 3 adds it to B5.
