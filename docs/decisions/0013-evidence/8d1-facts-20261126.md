## F1. Is a new guest's row inserted with its task?

Yes, for all four. Each path builds a `tasks.Request` whose `Companion`
inserts the guest's row in the transaction that creates the task
(`tasks.Engine.Submit` → `Store.Create(ctx, t, sourceIP, req.Companion)`,
`internal/tasks/engine.go`):

| Path | File, function | Companion |
|---|---|---|
| VM create | `internal/vm/lifecycle.go`, `Service.CreateVM` | `s.store.InsertTx(ctx, tx, vm, …)` |
| VM clone | `internal/vm/snapshots.go`, `Service.CloneVM` | the snapshot's row (when it takes one), then `s.store.InsertTx(ctx, tx, vm, …)` |
| Jail create | `internal/containers/tasks.go`, `Service.CreateContainer` | `s.store.InsertTx(ctx, tx, s.nodeID, c)` |
| Jail clone | `internal/containers/snapshots.go`, `Service.CloneContainer` | the snapshot's row, then `s.store.InsertTx(ctx, tx, s.nodeID, c)` |

So a guest row exists from the moment its create or clone task is
accepted, as D30 assumes. A replay by idempotency key creates nothing and
answers the first task and the row it made (`LookupKey` in `CreateVM`,
`Service.replay` in the other three).

## F2. After a failed or cancelled create or clone task

| Path | Failure in the handler | Cancelled before it started |
|---|---|---|
| VM create (`runCreate`, `undoCreate`, `internal/vm/lifecycle.go`) | `undoCreate` deletes what was made, then the rows; if the host delete fails the row **stays, unprovisioned** | the row **stays, unprovisioned** (`Engine.Cancel` moves a pending task to cancelled; no hook runs) |
| VM clone (`runClone`, `undoClone`, `internal/vm/snapshots.go`) | `undoClone`: the row is removed when the datasets could be destroyed, otherwise it **stays, unprovisioned** | stays, unprovisioned |
| Jail create (`runCreate`, `destroyAfterFailure`, `internal/containers/tasks.go`) | the jail root is destroyed; the row **always stays, unprovisioned**, "for the user to delete" (also when `CreateJailRoot` itself failed) | stays, unprovisioned |
| Jail clone (`runClone`, `undoClone`, `internal/containers/snapshots.go`) | `undoClone`: the row is removed when the dataset could be destroyed, otherwise it **stays, unprovisioned** | stays, unprovisioned |

So the outcome of a task does not say whether the guest exists: a failed
task may leave the row or not. Reconciliation must look at the guest on
the agent by its name, not infer from the task (amendment 6).

## F3. Names

- VM: `^[A-Za-z0-9][A-Za-z0-9._-]{0,62}$` (`nameRE`, `internal/vm/validate.go`), ASCII, 1 to 63 bytes, case-sensitive.
- Jail: the same expression (`nameRE`, `internal/containers/service.go`).
- Agent schema (`migrations/sqlite/agent/0001_initial_schema.sql`):
  `virtual_machines.name TEXT NOT NULL UNIQUE` and `containers.name TEXT
  NOT NULL UNIQUE` — unique per table on the agent (that is, per node and
  per kind), not per `node_id`; a VM and a jail may share a name. SQLite's
  default (BINARY) collation: case-sensitive. A taken name is
  `vm_name_taken` (`internal/database/vmstore.go`) or
  `container_name_taken` (`internal/database/containerstore.go`), 409.
- Neither name can be changed after the create: `models.VMUpdate` and
  `models.ContainerUpdate` have no name field (`pkg/models`).

D12's name rule (UTF-8, 1–255 bytes, no control byte) admits every name
the agent admits.

## F4. A new 503 code from the agent to the public API

- The agent writes it with `httpkit.Fail` (`internal/httpkit/fail.go`),
  which takes the status from `httpkit.StatusForCode`; a code not in the
  map is written as 500 internal_error.
- `agentclient.responseError` (`internal/agentclient/client.go`) passes a
  `models.Error` on only when `StatusForCode[code]` exists **and** equals
  the status the agent answered; anything else becomes a plain error, which
  the API answers as 500.
- `h.fail` (`internal/api/session.go`) uses `statusForAuthCode` for the
  auth codes and otherwise `httpkit.Fail`, i.e. `StatusForCode` again.
- So `node_draining` needs one entry, `StatusForCode[CodeNodeDraining] =
  503`, and it reaches the client unchanged with its details. The access
  audit's failure/denial split is in `auditVM` (`internal/api/vms.go`) and
  `auditContainer` (`internal/api/containers.go`): codes other than
  invalid_request, agent_unavailable, queue_full and shutting_down are
  recorded as denials, so `node_draining` must be added to that list (D9).

## F5. Is root an allowed peer of the agent's socket?

Yes. `config.Config` defaults (`internal/config/config.go`, the defaults
function at `c.Socket.AllowedUsers == nil`): outside dev mode
`allowed_users` is `["root", "skep"]`; the sample
(`packaging/etc/agent.json.sample`) says the same. `skep-setup` writes
only `storage` and `network` into agent.json (`AgentConfig`,
`builder.agentJSON`, `internal/setup/plan.go`), so the default applies on
every host it set up (blazanov's agent.json, read on the host 2026-11-26,
has no `socket` key). The socket is root:skep 0660 in /var/run/skep
(root:skep 0750); `cmd/skep-agent/main.go` `listenSocket`.

## F7. List order and pages on the agent

- `/vms`: `vm.Service.VMs` (`internal/vm/service.go`) → `VMStore.List`
  (`internal/database/vmstore.go`): `ORDER BY name`, keyset cursor
  `name > cursor`; default 50, at most 200 (`DefaultPageSize`,
  `MaxPageSize`).
- `/containers`: `containers.Service.Containers` → `ContainerStore.List`
  (`internal/database/containerstore.go`): `ORDER BY c.name`, cursor
  `c.name > cursor`; default 50, at most 200.
- Pages are separate reads, not one snapshot: a guest created between two
  page reads whose name sorts before the cursor is missed by that listing.
  A guest that is only missing from a listing must therefore never be
  removed on that evidence alone (D30 e: a single read by ID, and only its
  "not found" counts).

## F8. The web interface and `503 no_quorum`; the serial console

- `web/src/api/client.ts`: an error answer becomes an `ApiError` with
  status, code, message and details; only `agent_unavailable` (503) and
  401 `unauthenticated` are treated specially. `no_quorum` is shown as an
  ordinary error with its message (`InlineError` on the form or page).
  Nothing retries a write by itself.
- The console never opens by itself: `VMDetailPage.tsx` mounts
  `SerialConsole` only after the user presses "Console" (`showConsole`
  starts false); `SerialConsole.tsx` opens the WebSocket on mount. A
  refused upgrade (503) closes with 1006 and the page says the console
  could not be reached.
