# Step 8c-1: facts read from the code before the build (2026-11-25)

Read on `main` at `bcc9cc5` (step 8b-2b merged), before any code of step
8c-1 was written. Each fact names the file and function it was read from.

## 1. What `store.Node.Apply` returns, and its time limit

`internal/cluster/store/store.go`, `(*Node).Apply`: it encodes the entry,
calls the library's `raft.Apply(raw, applyTimeout)` with `applyTimeout =
10 * time.Second`, and returns `(clusterstate.Result, error)`:

- `store.ErrNotLeader` when the library answers `raft.ErrNotLeader`:
  nothing was written;
- `ErrOutcomeUnknown` wrapping any other library error;
- otherwise the state machine's `Result` and `res.Err`, so a refusal comes
  back both in the result and as an error wrapping
  `clusterstate.ErrRefused`.

The 10 s bounds only the hand-off to the leader's loop (hashicorp/raft
v1.8.0 `api.go` `ApplyLog`: the timer covers the send on `applyCh`, and
its expiry is `ErrEnqueueTimeout`, which `Apply` maps to
`ErrOutcomeUnknown` although nothing was written). The wait for the commit
has no timer of its own: it ends when the entry is applied, or with
`ErrLeadershipLost` when the leader steps down after its lease without a
majority. The `Result` carries no log index (`clusterstate.Result`:
`Duplicate`, `Err`, `Entry`, `Events`); the future's `Index()` is not read.

A refusal's error is text only: `clusterstate.machine.go` `apply` wraps
the reason as `fmt.Errorf("%w: %s", ErrRefused, err)`; there is no code.

## 2. How `remove` and `admit` reach the leader

`internal/cluster/service/peer.go`:

- `(*Service).Admit` (the local socket): on the leader it calls
  `admitAsLeader` directly; on a member that is not the leader it calls
  `toLeader(ctx, raftnet.OpAdmit, forwardAdmit{Request, Actor, OpID}, &res)`.
  The operation ID is made once, by the node the command ran on.
- `toLeader` reads the leader's ID from the store, its member entry from
  the machine, and calls it with `callMember` (either of its pins). A
  `raftnet.PeerError` is mapped to a `localapi.OpError` with the peer's
  code and an HTTP status; `raftnet.OutcomeUnknownError` to
  `outcome_unknown`; an unreachable leader to `no_leader` ("nothing was
  sent").
- On the leader, `HandlePeer` case `raftnet.OpAdmit` (and `OpWithdraw`)
  decodes strictly, then calls `notLeader()` **before** `admitAsLeader`,
  which computes every refusal (V2 of the 8b-2b review: `notLeader`
  answers `unavailable` while the barrier of the current term has not
  succeeded, `service.barrierTerm != store.Term()`).
- `remove`: `internal/cluster/service/removal.go` `(*Service).Remove` and
  the peer case `raftnet.OpRemove` → `handleRemove`, the same shape with
  its own 60 s limit (`localapi.RemoveTimeout`).
- Write errors on the leader: `applyError` maps `ErrRefused` to
  `409 refused`, `ErrNotLeader` and `ErrOutcomeUnknown` to
  `503 not_committed`.

## 3. The cluster audit's record encoding, and a new field

`internal/cluster/audit/audit.go`: `Record` is a struct encoded with
`encoding/json`; every field but `seq`, `local_time`, `kind` and
`prev_hash` has `omitempty`. `hash` is the SHA-256 of the encoding without
`hash` (`canonical`). `Verify` decodes each line with
`DisallowUnknownFields`, re-encodes it (`line`) and requires the bytes to
equal the line ("not the record's canonical encoding (changed)"), then
checks the hash.

A new field with `omitempty` keeps every old line verifying: an old line
has no such key, decodes to the zero value, and re-encodes without it, to
the same bytes and the same hash. A field **without** `omitempty` would
break every old line. A new build's line that carries the new key is
refused by an old build's `Verify` (unknown field): only the new build
reads its own new records.

`clusterstate.AuditEntry` → `(*Log).AuditEntry` copies the fields one by
one into a `Record`; the machine builds the `AuditEntry` in `auditOf`
from `state.describe(e)` (`describe.go`), which knows only member and
pending entries.

## 8. Can skep-cluster's service run with the API account equal to its own account?

Yes, nothing refuses it. `cmd/skep-cluster/serve.go` `runServe` refuses
only `euid == 0` (`errRoot`) and an API account with UID 0; `serveSocket`
passes `AllowedUIDs: []uint32{0, apiUID}` and `HandlerOptions{APIUID:
apiUID}`. `internal/cluster/localapi/handler.go` `authorize` admits
`peer.UID != 0 && peer.UID == apiUID && op.API`. So a service started by
an ordinary user with `-api-account` naming that same user admits its own
UID as "the API". The package comment of `localapi/listener.go` says the
service account itself is not an allowed peer: that is true on an
installed host (two accounts, 409 and 410) and is not enforced by the code.
A test build (D22) can use this for the browser test's stack.

`service.CreateCluster` (`internal/cluster/service/wipe.go`) creates the
key, bootstraps the store and writes `cluster.init`; it does not check the
UID (`runInit` does, before it drops to the service account).

## 9. Other facts the build depends on

- `raftnet` node-to-node message limit: `maxPeerMessage = 256 << 10`
  (`internal/cluster/raftnet/peerrpc.go`), `PeerTimeout = 30 s`.
- The local API client reads at most 4 MiB of an answer
  (`localapi/client.go` `get`, `post`); the server reads at most 1 MiB of
  a request body (`handler.go` `withTimeout`); every operation but remove
  has `RequestTimeout = 15 s`.
- `localapi.actorOf` names root `"root"` and every other caller
  `"unknown"`; the API account's operations have no actor of their own yet.
- The access audit's local actor is `audit.LocalActor(uid)` =
  `"local:<uid>"` (`internal/audit/audit.go`).
- `api.db`: `users.username` is `UNIQUE`; `password_hash` has `CHECK
  (password_hash LIKE '$argon2id$%')`; `sessions.user_id` references
  `users(id) ON DELETE CASCADE` (`migrations/sqlite/api/0001`, `0002`).
- The leader's barrier: `internal/cluster/service/leader.go` `leaderStep`
  is called only from `step`, once per `Run` tick (1 s), after
  `joinStep`, `waitsStep` and `statusStep` (`service.go` `step`).
- Snapshot formats: `clusterstate/machine.go` `Snapshot` writes format 2
  while no member was removed, 3 after a removal, 4 only while a member has
  a next pin; `Restore` reads 1 to 4 and refuses a higher one.
- `skep-cluster join` asks for the cluster ID on the terminal or takes
  `-cluster-id` (`cmd/skep-cluster/join.go` `confirmJoin`); the API's
  `api.db` belongs to the `skep` account (409), which the `skep-cluster`
  account (410) cannot read.

## Deviations

None of the facts contradicts a fixed decision. Two need a choice the
decisions do not make; both are listed in the stop report under
"Decisions for review":

- D21 says the join's confirmation lists the host's users "read through
  the stage as the service account". `skep-cluster`'s stage runs as the
  `skep-cluster` account, which cannot read `api.db` (fact 9). The build

  machine sets it in `Result`.
