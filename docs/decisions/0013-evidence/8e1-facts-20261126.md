## F1. The agent's "requested" audit entries

- **Submit.** `tasks.Engine.Submit` (internal/tasks/engine.go) builds a
  `tasks.Task` and calls `Store.Create`. The "requested" entry of an
  accepted task is written inside that transaction by
  `database.TaskStore.Create` (internal/database/taskstore.go,
  `insertAudit(... audit.Entry{... Phase: audit.Requested ...})`) with **no
  `Details`** today. A refused submission is written by `Engine.refuse` with
  `Details {error_code, error}`.
- **Cancel.** `tasks.Engine.Cancel` builds the entry itself with
  `Details {task_type, task_status}` (and `error_code` on a refusal) and
  hands it to the store (`Transition.Extra`, `Store.RequestCancel`) or
  writes it (`audit.Write`).
- **Where two more details go without a schema change:** `audit_log.details`
  is a JSON column (internal/audit/audit.go, `Entry.Details`). Two optional
  values on `tasks.Request` and `tasks.CancelRequest`, copied onto the new
  `tasks.Task` (not stored in the `tasks` table) and added to the details in
  `TaskStore.Create`, `Engine.refuse` and `Engine.Cancel`. The values reach
  the services from `internalapi`'s `submission` (vms.go) and the container
  and template equivalents, which copy `agentproto.CallerFrom`. **(shapes
  the build)**
- **A header the agent does not know:** ignored. `agentproto.FromHeaders`
  reads only the five named headers; `internalapi.withCaller` validates only
  those (internal/internalapi/handler.go). An 8d-2 agent given
  `Skep-Origin-Node`/`Skep-Envelope` drops them silently, which is harmless:
  skep-api and the agent come from one package and are refused when their
  builds differ (`agent_version_mismatch`).
- **Header size limit:** `internalapi.NewServer`
  (internal/internalapi/server.go) sets `MaxHeaderBytes: 16 << 10` (16 KiB):
  a 4096-byte envelope fits.

## F4. Error codes and their statuses

- `httpkit.StatusForCode` (internal/httpkit/fail.go) maps `models` codes for
  `httpkit.Fail`; `statusForAuthCode` (internal/api/session.go) maps
  `internal/auth` codes in `handler.fail`; `statusForClusterCode`
  (cluster.go) the cluster codes. A code in none of them, reaching
  `httpkit.Fail` as a `*models.Error`, becomes 500 `internal`. The four new
  codes are written directly with `httpkit.WriteErrorDetails`, and are also
  added to `StatusForCode` so that `Fail` keeps their 503.
- The OpenAPI document lists error codes in prose in `info.description`
  (the "Errors" and quorum paragraphs) and per response; there is no enum of
  codes (api/openapi.yaml, the `Error` schema has `code: string`).
- skepctl prints any API error it does not explain itself through
  `client.APIError.Error()` (pkg/client/client.go): "MESSAGE (HTTP 503,
  CODE), request ID". `session.explain` (cmd/skepctl/session.go) special-cases
  only a changed key, an untrusted certificate and 401 `unauthenticated`. A
  503 `node_behind` is printed with its message and code; nothing else is
  needed.

## F5. Member.APIPin today

- **Declared:** `clusterstate.Member.APIPin` (`api_pin`, omitempty)
  (internal/cluster/clusterstate/machine.go).
- **Validated:** `checkMemberValues` refuses a non-empty one ("an API pin is
  not accepted before step 8e"); it is called for `cluster.init` and
  `pending.create` (machine.go, `state.apply`). `member.join` builds the
  member from the pending entry, which has no API pin. No other read.
- **Copied:** `membership.FromMembership` copies it to
  `membership.Member.APIPin` (internal/cluster/membership/membership.go);
  `membership.File.validate` does not look at it. The snapshot carries it
  inside `Members` (`Machine.Snapshot`/`Restore`). `localapi.Status.Members`
  and `memberapi.View.Members` are `[]clusterstate.Member`, so the status
  carries it when set. `describe.go` and the cluster audit do not record
  it. The join answer and the admission (`joincode.Node`) have no API pin.
- **What an 8d-2 build does** with a snapshot holding an API pin: its
  `Member` type has the field, so a snapshot of format 6 or lower would be
  read and the pin kept; a format 7 snapshot is refused ("snapshot format 7
  is unknown to this build", `Machine.Restore`). That is why D5 raises the
  format. With a `membership.json` holding an API pin: read and accepted
  (the field exists, nothing validates it); the file's format numbers stay.
  With a `member.api_key` entry: its machine stops ("entry type
  "member.api_key" is unknown to this build", `Machine.apply`), which is
  D8's reason for the guard.

- The TLS handshake of an `http.Server` is bounded by the shortest non-zero
  of `ReadHeaderTimeout`, `ReadTimeout` and `WriteTimeout`; `IdleTimeout`
  does not bound it. D18's 10 s handshake bound is `ReadHeaderTimeout: 10 s`
  (the shortest of the three).
- `http.Transport{DisableKeepAlives: true}` makes one handshake per request.
- **(shapes the build)** A TLS 1.3 client whose certificate the server
  refuses in `VerifyConnection` **completes its handshake** (`tls.Dial`,
  `Handshake` return nil) and even writes its request; the refusal arrives
  at the **first read**: a `*net.OpError` with `Op == "remote error"` whose
  text is `remote error: tls: bad certificate` (the alert type is not
  exported and `tls.AlertError` does not match). `http.Client.Do` returns it
  wrapped in a `*url.Error`. The receiver never parsed the request: the
  origin treats exactly this error as "nothing was sent" (D35), and every
  other error after the handshake as "unknown".
