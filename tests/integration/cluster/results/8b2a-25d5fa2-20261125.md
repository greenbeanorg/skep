## The defect found in 4.5 (run A) and its fix

`hashicorp/raft` v1.8.0 `GetConfiguration()` is answered from a copy outside the main loop and its `Index()` is always 0, so "is the latest configuration committed" always read as yes: smith's health named the wrong step, and the leader loop's "nothing while the latest configuration is uncommitted" (D5e) did not hold literally. Safety was not affected (a final entry at a higher index cannot commit before the configuration entry below it, and smith had lost the leadership). Fixed in `25d5fa2`: `store.Node.Configuration` reads from the log whether a configuration entry is stored above the commit index; the in-process test now checks the health text and the value; the library-facts table in the architecture page is corrected. All three hosts were upgraded to `25d5fa2` (star first while removed, then wiped and rejoined, then langrishe and smith, two of three voters up throughout) and 4.5 was run again.
